# 新版统一认证与自动滑块

学校的统一认证目前使用 `/authserver/login`。旧 `/lyuapServer` 的算术图片接口不能直接替换成滑块接口。

## 运行 Demo

在终端进入 Swift 包目录后运行：

```sh
# 不提交账号密码，仅实测取图、匹配、加密和服务端滑块校验
swift run WUSTDemo --slider-captcha

# 输入账号和密码，使用新版原生登录；密码由终端隐藏读取
swift run WUSTDemo --native-login
```

也可以直接在 Xcode 中选择 `WUSTDemo` / `My Mac`，按 `⌘R`，在底部控制台输入账号并选择 `4`。Xcode 下使用安全密码弹窗；终端下使用隐藏密码输入。无需配置启动参数。

Demo 的滑块单测入口和新版自动登录入口遇到滑块失败或临时网络错误时，最多尝试 **3 次总计**（首次加最多两次重试）。每轮最多提交一次服务端校验；定位不可靠则立即换图，不增加三次额度。每个校验轮次若连续 10 张图片都不可靠，则以 `challengeRefreshLimitExceeded(10)` 停止并写日志；这一停止不会被 Demo 再重试。不会与库内重试相乘。取消、密码或额外认证问题不自动重试。库的默认滑块次数仍为 3，可通过 `loginWithAuthServer(password:maxSliderAttempts:)` 调整。

### 保存本地测试账密

首次选择新版自动登录（菜单 `4` 或 `--native-login`）时，输入的账号密码会自动保存到 `~/Library/Application Support/WUSTDemo/login.enc`。以后运行 Demo 自动读取账号，选择新版登录时也自动读取密码，无需重复输入；终端直接运行 `swift run WUSTDemo --native-login` 即可重复测试。Xcode 仍可按 `⌘R` 后选择 `4`，或给 Scheme 加上 `--native-login` 启动参数。

文件使用 AES-GCM 加密，密钥保存在本机 Keychain。目录权限为 `0700`、文件权限为 `0600`，不会在控制台打印账密。该文件位于仓库外，不会被 Git 提交。

```sh
# 单独录入或更新账密，不进行网络登录
swift run WUSTDemo --update-login-file

# 显示文件位置，不读取或显示账密
swift run WUSTDemo --login-file-path

# 清除本地账密文件；不影响其他 Demo 会话凭据
swift run WUSTDemo --clear-login-file
```

文件损坏或密钥缺失时，使用 `--update-login-file` 重新录入。此保存逻辑属于 Demo；库的 App 登录接口仍由调用者提供密码。

原有网页登录入口仍可使用。`--native-login` 遇到服务器要求额外验证时会明确报错，不会把未完成认证当作成功。

### Demo 失败诊断

每次生成轨迹时，Demo 会在回调返回前立即将完整 `a/b/c` 点数据写入 `~/Library/Application Support/WUSTDemo/Diagnostics/Trajectories/trace-时间-运行标识-round轮次-序号.json`，每段一个文件，不等待整轮流程结束。文件包含生成时间、轮次和状态；收到服务端业务码或后续错误时原子更新同一个文件。成功、失败、取消及尚未取得结果的轨迹均保留，重试和新运行不会覆盖旧轨迹。正常记录不自动清理；磁盘写入失败会明确报告。目录权限为 700、文件为 600。此自动存档属于 Demo，库本身仍通过可选诊断回调交付数据，不自行写文件。

控制台会在结束时打印“逐次轨迹目录”，完整日志内另有各文件路径。即使程序在生成后、校验前中断，已写入的 JSON 仍可查看，并标为尚无校验结果。

Demo 将每轮 `[滑块诊断 N/3 +耗时ms]` 写入独立日志文件：登录页与取图、解码、定位、轨迹生成、等待、校验提交各阶段，以及请求前/响应后的 Cookie 数量、HTTP 状态、响应主机是否一致、定位最高分、竞争位置分数与分差、定位停止原因、原图偏移、组件位移、轨迹点数、运动时长、纵向范围和服务器业务码。仅输出数量与数值，不输出 Cookie 值、账号密码、图片、表单令牌、加密密钥或 sign。

成功、取消或最终失败时，Demo 自动将完整阶段记录写入 `~/Library/Application Support/WUSTDemo/Diagnostics/slider-时间-标识.log`；控制台只显示结果与文件路径。三轮可重试失败后，文件额外包含 `===== 滑块三轮失败汇总 =====`。三轮均为业务码 0 表示都完成提交并被服务器拒绝，不能据此确定是坐标、轨迹还是会话规则导致；未取得业务码则依据最后阶段区分本地定位、网络或响应解析问题。可直接提供该日志文件继续排查。目录权限为 700、日志为 600，不需要提供账号密码。

2026-11-25 用 `WUSTDemo --slider-captcha` 实际复现一次三轮失败：各轮取图和校验均为 HTTP 200、主机一致、校验前 Cookie 数量均为 2；定位分数分别为 0.966、0.957、0.962，轨迹时长为 1000、1091、1000 毫秒，三轮业务码均为 0。该次运行排除了“请求未发出、解码未完成”等情形，但不证明 Cookie 内容、定位或轨迹满足服务端条件。未提交账号密码。

库内诊断是可选的 `diagnostics` 回调，默认不产生输出；Demo 在 `loginWithAuthServer`、`beginSession`、`solveAndVerify` 上传入观察器。

## App 调用

复用现有的 `WUSTLoginClient`：

```swift
let result = try await client.loginWithAuthServer(password: password)
if case .authenticated = result {
    let info = try await client.fetchStudentInfo()
}
```

此入口使用一个新的临时 URLSession 访问登录页、读取表单动态参数、获取并解决滑块、提交加密后的密码。最后通过学生信息接口确认登录账号，验证成功才替换 client 的教务会话。网络或识别失败不应视为密码错误。

目前此入口接入的是教务会话，不生成旧 `/lyuapServer` REST 接口使用的 TGT，也不承诺跨进程恢复或其他业务系统的登录。独立短信登录使用 `sendLoginSMSCode(to:)` 与 `loginWithSMSCode(_:)`，Demo 菜单 `5` 或 `--sms-login` 可运行，见 [短信登录接入](Login.md#新版手机号短信登录)。其他额外认证流程仍可使用网页登录入口。

## 单独使用滑块模块

```swift
let session = URLSession(configuration: .ephemeral)
defer { session.finishTasksAndInvalidate() }
let service = AuthServerCaptchaService()
try await service.beginSession(using: session)
let solution = try await service.solveAndVerify(using: session)
// 当前 session 已经通过本次滑块校验；后续登录提交继续使用它。
```

若已在同一会话获取登录表单，直接调用 `solveAndVerify`，避免重新初始化登录页改变已有流程状态。

`SliderCaptcha` 保留 `bigImage`、`smallImage`、`tagWidth`、`yHeight`。图片格式和尺寸不固定；小图末尾的 16 字节是本次挑战的加密材料，必须保留原始 Base64，不能用重编码后的 PNG 替换。不要记录或持久化它、登录表单令牌、Cookie、密码或加密后的提交内容。

`SliderCaptchaSolver` 使用透明遮罩内的灰度归一化相关性寻找位置，允许目标区域亮度改变；匹配分数过低或存在相近的竞争位置就返回 `noReliableMatch`。它把原图像素位移转换成组件坐标，无须 OCR 或训练模型。`AuthServerCaptchaService` 按官网格式构造程序化移动采样，并使用 AES-CBC/PKCS7 加密校验内容；只有服务器 `errorCode == 1` 才返回成功。

定位现在使用 Accelerate 批量计算灰度和相关性，预先计算采样索引，并复用同尺寸的拼图解码结果。本机 Debug 编译下，14 张实际挑战图片的定位结果与原实现一致，解码与定位耗时中位数由约 73 毫秒降至 5.3 毫秒。这是该批样本的本地耗时，不包含取图、运动等待和服务端校验，也不代表其他设备上的耗时。

匹配分数不是服务端通过概率。部分服务端拒绝的样本在独立轮廓检查中也得到了相同位置，但服务端未返回具体拒绝原因；缩短运动等待、调整运动采样及编码格式的试验尚未形成稳定的通过率改善，此次保留原水平路径，按下述调整放慢短距离移动并加入纵向抖动，不降低匹配阈值。

默认最多提交 3 次服务端校验，允许范围为 1–5 次。定位不可靠的图片在提交前立即丢弃，不计入此次数；每轮连续 10 张不可靠时触发独立的换图上限并停止。网络错误、响应格式错误和取消会直接传出；不要针对同一挑战反复猜测坐标。

### 2026-11-25 点数提高到 61 点

每条生成轨迹现在为 **61 点**（起点加 60 个移动点），不再随短距离降至 13 点。当前总时长统一为 **1400 毫秒**，适用于所有移动距离；采样间隔按累计时间戳缩放，末点仍等于目标位移。`solveAndVerify` 的轨迹等待时长也为 1400 毫秒，取图、定位和网络校验耗时另计。此调整未验证线上通过率。

### 纵向采样微偏移

每个中间采样点在原竖向坐标上叠加随机正负 0.001–0.099 组件单位的偏移，以 0.001 为步进；原竖向坐标为 0 时，微偏移沿该条轨迹选定的方向，保持向单侧偏移。起点、末点、水平坐标、点数和总时长不变。完整 `trajectoryPayload` 直接记录并提交这些实际坐标，日志查看器无需自行生成偏移。此改动未验证线上通过率。

### 2026-11-25 恢复旧轨迹并放慢短距离移动（历史调整）

已按要求撤回候选的随机轨迹生成器，恢复旧算法的等距水平移动与点数规则。纵向目前改为向单侧缓慢偏移并叠加小幅相关噪声：每条轨迹随机选择向上或向下，基准总偏移 6–12 单位，噪声限制在 ±0.8 单位，坐标取整后保留小幅阶梯与回摆，末点不强制归零；已撤回之前每步 2–4 单位的大幅上下抖动。水平终点和计时规则不受纵向抖动影响；是否提高通过率尚未实测。原始轨迹不足 1000 毫秒时，按比例拉长各采样间隔，使轨迹总时长达到 1000 毫秒；原本超过该时长的轨迹保持原速。例如，46 单位位移由 390 毫秒变为 1000 毫秒，94 单位位移由 805 毫秒变为 1000 毫秒，183 单位位移仍为 1430 毫秒。使用累计时间戳缩放，避免逐点取整导致总时长偏差。

`solveAndVerify` 每次只生成一份 payload，等待时间和加密提交共用它。App 登录接口不变，个人手拖轨迹文件没有打包到库中。

1000 毫秒是待验证的调参值，并非已知的服务端接受条件。此前匿名对照中，旧版和已撤回的候选随机算法各 6 次均被服务端拒绝，不能由此认定短距离速度是唯一原因。本次调整的测试验证时长、终点、路径边界和长距离速度保持；尚未验证调整后的线上通过率。

### 2026-11-24 边缘复核试验

临时原型在灰度分数最高的 20 个偏移上计算水平、垂直灰度梯度相关性，再将灰度与梯度分数等权合并。8 张新挑战中，原算法接受的 7 张与原型定位完全一致；另 1 张原算法因可靠性不足放弃，原型给出的坐标没有真值验证，因此未提交。

保持现有会话与运动时序，按样本顺序交替提交原算法或原型的结果：原算法 3 次、原型 4 次，均被服务端拒绝。各次使用独立匿名会话和新挑战，每张最多提交一次，未提交账号密码。两组不是同图对照，样本量也不足以估计稳定通过率；此次没有证据支持用边缘原型替换现有定位器。服务端没有提供具体拒绝原因，后续仍需核对官网成功交互与库请求的差异。

### 2026-11-25 Safari 风格请求头对照

按要求为当前原生认证链路统一设置桌面 Safari 18.0 兼容配置：登录页和表单使用导航类 Accept，滑块取图/校验使用 JSON Accept 与 X-Requested-With；统一 User-Agent、Accept-Language，同源请求补上登录页 Referer，POST 补上 Origin。原生登录表单 URL 会作为滑块请求的 Referer，保留 service 参数。Cookie、压缩、Host 与 Content-Length 仍由 URLSession 管理，不复制 Safari 中已有的 Cookie。

诊断文件增加 `请求头配置=Safari-compatible/18.0`，便于确认运行的是新配置。这是 HTTP 头配置，不等于切换到 Safari/WebKit 运行环境。未修改定位、轨迹、等待时间和重试预算。

本轮先用改动前配置运行一次匿名 Demo，再用 Safari 风格头运行一次；两轮均完成 3 次服务端校验，业务码全部为 0，未观察到改善。两轮使用独立会话和新挑战，不是同图对照，也未提交账号密码。改动前日志为 `slider-2026-11-25T13-00-15Z-8DF4A1B9.log`，改动后为 `slider-2026-11-25T13-04-37Z-21744652.log`。这组小样本不能证明所有请求头因素都无关。

### 2026-11-24 请求与加密复核

重新读取当前官网的 `ids-sliderCaptcha.js`、`longbow.slidercaptcha.js` 与 `encrypt.js`。临时请求原型增加浏览器常见 User-Agent、Referer、POST Origin，并对 GET 增加时间戳和禁用本地缓存，保持原定位与运动数据。在另外 8 张新挑战中，1 张因匹配可靠性不足未提交，7 次服务端校验全部被拒绝。这是组合变量探索，不能据此判断某个请求头的单独作用，也没有证据支持将这组改动并入正式实现。

另外固定测试用随机前缀、IV 和虚构密钥，将 Swift/CommonCrypto 与当前官网 JavaScript/CryptoJS 直接比较：载荷长度为 0、15、16、17、1024 字节的五组密文完全一致。此结果验证这些输入下的加密兼容性，不证明会话状态、移动轨迹或坐标一定符合服务端要求。

## 验证范围

### 轨迹诊断数据

Demo 现在额外记录 `trajectoryPayload` 完整 JSON，包含 `canvasLength`、`moveLength` 与每个 `a/b/c` 点。该诊断事件使用本轮等待及提交共用的同一份 payload，不重新生成随机点。记录不含图片、密钥、账号密码或 Cookie 值。旧日志缺少逐点数据时仅显示摘要，不根据范围补造轨迹；新日志需用更新后的 Demo 生成。此工具只读取本机文件，不访问认证服务。

此前曾在实际匿名会话中完成服务端滑块校验，但上述最新两轮试验没有取得成功；先前成功不能视为当前稳定通过率的保证，也不等于已完成真实账号登录。新账号密码入口需要使用者在本机实际运行验证。测试覆盖亮度变化后的定位、尺寸换算、非法图片、加密协议、服务端拒绝、表单令牌和表单来源检查。

协议依据：学校当前公开的 `ids-sliderCaptcha.js`、`longbow.slidercaptcha.js`、`encrypt.js` 和账号登录表单。服务器规则变化时需要重新核对。
